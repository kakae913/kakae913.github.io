## 1. Fuzzing이란?

Fuzzing(퍼징)은 프로그램에 의도적이고 무작위적인 입력값을 대량으로 집어넣어 크래시(crash), 메모리 오류, 예외 동작 등의 취약점을 찾아내는 자동화된 소프트웨어 테스트 기법이다.

Fuzzing을 하는 이유는 개발자가 직접 테스트를 짤 때는 자신이 예상하는 정상 케이스 위주로 작성하기 때문이다. 이랬을 때 개발자가 생각지 못한 입력값이 들어오면 문제가 생길 수 있기에, 그것을 막고자 하는 게 Fuzzing이다.

## 2. Code Coverage

코드 커버리지(Code Coverage)는 작성된 테스트 코드가 전체 소스 코드 중 얼마나 많은 부분을 실제로 실행하고 검증했는지를 백분율(%)로 나타내는 소프트웨어 테스트 지표이다.

코드의 구조는 크게 **구문(Statement), 조건(Condition), 결정(Decision)**이다.

### 2-1. 구문(Statement)

*“각 문장이 최소 한 번은 실행됐는가?”*

```c
void test(int x) {
    int a = x + 1;        // 구문 1
    int b = x * 2;        // 구문 2
    if (x > 0) {
        printf("양수\n"); // 구문 3
    }
    printf("끝\n");       // 구문 4
}
```

| 입력 | 실행된 구문 | 커버리지 |
| --- | --- | --- |
| `test(-1)` | 1, 2, 4 | 3/4 = **75%** |
| `test(1)` | 1, 2, 3, 4 | 4/4 = **100%** |

### 2-2. 조건(Condition)

*“각 조건식이 참(T)과 거짓(F)을 모두 가졌는가?”*

```c
if (a > 0 && b > 0) {
//  ①a>0      ②b>0   ← 조건이 2개
    ...
}
```

| 테스트 | ①a>0 | ②b>0 | 커버 |
| --- | --- | --- | --- |
| (1, 1) | T | T | ①T, ②T |
| (-1, -1) | F | F | ①F, ②F |
| → 합치면 | T/F 모두 | T/F 모두 | **100%** |

여기서 문제는 위 두 개의 케이스만 봤을 때는 이미 a>0인 T,F를 봤고 b>0인 T,F를 봤다. 하지만 (1,-1)인 T,F 케이스와 (-1,1)인 F,T 케이스는 못 봤다는 문제점이 생긴다.

즉, 조건 하나하나는 커버했지만 조합은 커버 못한 경우가 생긴다.

### 2-3. 결정(Decision)

*“if/while 등 분기 전체(결정)가 참과 거짓을 모두 가졌는가?”*

```c
if (a > 0 && b > 0) {   // ← 이 if 전체가 True/False 양쪽?
    doA();              // True branch
} else {
    doB();              // False branch
}
```

| 테스트 | a>0 && b>0 결과 | 실행 경로 |
| --- | --- | --- |
| (2, 3) | **True** | doA() 실행 |
| (-1, 5) | **False** | doB() 실행 |
| → 결정 커버리지 | **100%** ✓ | |

## 3. 상황별 Fuzzing

### 3-1. White box testing

소스 코드를 가진 상태에서의 Fuzzing이다. 정적 분석과 결합해 취약점 위치를 사전에 좁힐 수 있다.

**장점:** 커버리지 정확, 속도 빠름, 코드 경로 완전 파악

**단점:** 소스코드가 있어야만 함 (오픈소스, 자사 제품에 한정)

### 3-2. Gray box testing

바이너리는 있지만 소스는 없고, 일부 코드 정보만 가진 상태에서 퍼징한다. 소스코드 없이 컴파일된 바이너리에 계측을 삽입하거나, 실행 중 동작을 관찰해서 커버리지를 추출한다.

**장점:** 클로즈드 소스 바이너리에 적용 가능

**단점:** 화이트박스보다 느리고, 계측 정확도가 낮을 수 있음

*계측: 프로그램 실행 중 어디서 어떤 결과가 났는지 확인하기 위해 추가적으로 코드 안에 심는 기록 장치*

### 3-3. Black box testing

아무 정보 없이 퍼징한다. 순수하게 입력만 던져보는 방식으로 프로그램이 크래시 나는지 아닌지만 본다.

**장점:** 어떤 대상에든 적용 가능

**단점:** 커버리지 피드백이 없어서 매우 비효율적이고, 깊은 코드 경로에 도달하기 어렵다.

**어디서 쓰이나?**

소스도 없고, 바이너리 계측도 불가능한 경우에 사용한다.

- 네트워크 서비스 (서버에 패킷만 보낼 수 있음)
- 하드웨어 펌웨어
- 웹 애플리케이션 (API 퍼징)
- 폐쇄적인 임베디드 장비

## 4. Fuzzer란?

Fuzzing을 수행하는 도구(프로그램)이다.

### 4-1. AFL++ (AFLplusplus)

원본 AFL을 포크한 버전으로, 속도·뮤테이션·계측 면에서 원본을 뛰어넘는다고 주장하는 현재 벤치마크 1위 퍼저이다. 소스코드를 AFL++ 전용 컴파일러로 빌드하면 자동으로 계측이 삽입된다. 이후 `afl-fuzz` 명령어 하나로 퍼징을 할 수 있다.

**장점**

- 커버리지 추적이 정확하고 빠름 (소스 있을 때)
- QEMU/Frida 모드로 소스 없는 바이너리도 가능
- RedQueen, laf-intel 등 고급 기법 내장

**단점**

- 소스코드 없으면 성능이 뚝 떨어짐 (QEMU 모드는 2~5배 느림)
- Windows 대상 퍼징은 불편함 (Linux 중심)
- 복잡한 프로토콜/파일 포맷엔 별도 커스터마이징 필요

### 4-2. Jackalope (Google Project Zero)

소스 없는 클로즈드 소스 바이너리 전문 퍼저이다. Project Zero가 실제 취약점 연구에 쓰는 도구다. TinyInst라는 자체 바이너리 계측 엔진을 사용해서 소스 없이도 커버리지를 뽑아낸다.

**장점**

- 소스코드 없어도 커버리지 가이드 퍼징 가능
- Windows, macOS, Linux, Android 모두 지원
- 여러 머신에 분산해서 퍼징 가능 (서버-클라이언트 구조)
- 커스터마이징 쉽게 설계됨 (상속해서 확장)

**단점**

- AFL++보다 뮤테이션 전략이 단순함 (고급 기능 직접 구현해야 함)
- 화이트박스 상황에선 AFL++보다 느림

### 4-3. libFuzzer

프로그램 안에서 돌아가는 퍼저다. 별도 프로세스 없이 함수 하나를 직접 퍼징한다. AFL++은 프로그램을 매번 새로 실행하는 반면, libFuzzer는 프로그램 내부에 퍼저가 같이 빌드된다. 프로세스를 새로 띄우는 오버헤드가 없어서 초당 실행 횟수가 AFL++보다 훨씬 많다.

*오버헤드: 본래 목적 외에 추가로 드는 행위*

**장점**

- 속도가 매우 빠름 (in-process라 프로세스 생성 비용 없음)
- 설정이 단순함, 함수 하나만 감싸면 됨
- ASan, UBSan과 자연스럽게 연동
- Google이 Chrome, OpenSSL 등 대규모 프로젝트에 실제 사용 중

*ASan: 메모리 접근 오류를 잡아주는 탐지기*  
*UBSan: C 언어의 ''정의되지 않은 동작''을 잡아주는 탐지기*

**단점**

- 함수 단위로만 퍼징 가능 (전체 프로그램 퍼징 어려움)
- 타겟이 크래시나면 퍼저 자체도 같이 죽음
- Linux/macOS 중심, Windows 불편

### 4-4. honggfuzz

하드웨어 성능 카운터를 활용해서 커버리지를 더 정밀하게 추적한다. AFL++이 소프트웨어 계측으로 커버리지를 추적한다면, honggfuzz는 CPU가 직접 제공하는 하드웨어 정보도 활용한다.

*하드웨어 성능 카운터: CPU가 실행하면서 자동으로 여러 통계를 기록해주는 장치*

**장점**

- **Intel PT / perf 이벤트** 활용 → 소스 없어도 정밀한 커버리지
- 멀티코어 활용이 AFL++보다 효율적
- 지속적 퍼징(persistent mode)에서 매우 빠름
- 네트워크 서비스 퍼징 지원이 좋음

**단점**

- 설정이 AFL++보다 복잡
- Intel PT는 Intel CPU에서만 동작

| | **AFL++** | **Jackalope** | **libFuzzer** | **honggfuzz** |
| --- | --- | --- | --- | --- |
| **소스 필요** | 선택 | 불필요 | 필요 | 선택 |
| **실행 방식** | 외부 프로세스 | 외부 프로세스 | in-process | 외부 프로세스 |
| **속도** | 빠름 | 중간 | **매우 빠름** | 빠름 |
| **주 플랫폼** | Linux | Win/Mac/Linux | Linux/Mac | Linux |
| **주요 특징** | 범용 표준, 기능 가장 많음 | 클로즈드소스 바이너리 특화 | 함수 단위, 프로세스 재시작 없음 | 하드웨어 계측, 멀티코어 최적화 |
